# Προτεινόμενο Setup: MacBook (Intel, macOS Sequoia) + Windows Εργαστήριο + Ubuntu

Αυτό το έγγραφο απαντά συγκεκριμένα στο ερώτημα: *«ποιον compiler και ποια
IDE να χρησιμοποιήσω, ώστε το ίδιο έργο να δουλεύει ομαλά και στα τρία
περιβάλλοντα;»*

## 0. Επιβεβαίωση ότι κάθε παράμετρός σας καλύπτεται

| Ζητήσατε | Πού απαντάται εδώ |
|---|---|
| MacBook **Intel-based**, macOS Sequoia 15.7.8 | §1 και §2 — καμία οδηγία δεν προϋποθέτει Apple Silicon (βλ. σημείωση Intel παρακάτω) |
| Εργαστήρια με **Dev-C++** σε Windows | §2, ενότητα Windows |
| **VS Code + CLion** και τα δύο στο MacBook | §2, ενότητα MacBook |
| Τα 3 περιβάλλοντα να μη συγκρούονται λόγω compiler | §1 (CMake + αυστηρό C11 αντί για «ίδιος compiler παντού») |
| Windows: ΔΕΝ κάνουν push· MacBook: **push ΚΑΙ pull** | §3 «Ροή Git» (νέα ενότητα παρακάτω) |
| **Διαχωρισμός IDE από compiler/build system** | Αρχή σχεδιασμού σε όλο το έγγραφο — ρητά στο §1 |
| Άποψη για Apple Clang vs GCC παντού | §1, πλήρης αιτιολόγηση |

Αν κάτι από τα παραπάνω σας φαίνεται ημιτελές μετά την ανάγνωση, πείτε μου
συγκεκριμένα ποιο σημείο και θα το διορθώσω άμεσα.

## Η σύντομη απάντηση

**Ναι, χρησιμοποιήστε το Apple Clang στο MacBook σας — μην εγκαταστήσετε
ξεχωριστά GCC.** Η ομοιομορφία που χρειάζεστε την εξασφαλίζει το **CMake**
(ίδιες εντολές, ίδια δομή project παντού), όχι το να τρέχει κυριολεκτικά ο
ίδιος compiler binary σε κάθε μηχάνημα. Παρακάτω η αιτιολόγηση, και τι να
προσέξετε.

## 1. Γιατί Apple Clang και όχι GCC στο macOS

| | Apple Clang (Xcode CLT) | GCC μέσω Homebrew |
|---|---|---|
| Εγκατάσταση | Ήδη διαθέσιμο (`xcode-select --install`) | Επιπλέον βήμα (`brew install gcc`), ~500MB+ |
| Συμβατότητα με C11 | Πλήρης | Πλήρης |
| Ποιότητα μηνυμάτων σφάλματος | Πολύ καλή, συχνά σαφέστερη για αρχάριους | Καλή |
| Ταχύτητα | Πολύ γρήγορο | Γρήγορο |
| Ταίριασμα με Linux/Windows GCC | Διαφορετική "οικογένεια" compiler | Ίδια "οικογένεια" με Linux/MinGW |

Το μόνο πραγματικό επιχείρημα υπέρ του GCC θα ήταν να έχετε *κυριολεκτικά
τον ίδιο compiler* παντού. Στην πράξη αυτό δεν χρειάζεται εδώ, επειδή:

- Το `CMakeLists.txt` του μαθήματος ορίζει ρητά `CMAKE_C_STANDARD 11` και
  `CMAKE_C_EXTENSIONS OFF` — δηλαδή ο κώδικας γράφεται σε **αυστηρά πρότυπο
  C11**, χωρίς επεκτάσεις GNU. Ένα πρόγραμμα που μεταγλωττίζεται καθαρά με
  αυτές τις ρυθμίσεις θα συμπεριφέρεται ουσιαστικά ίδια σε Clang και GCC.
- Η ομοιομορφία «μία εντολή παντού» έρχεται από το CMake, όχι από τον
  compiler: `cmake -S . -B build && cmake --build build` δουλεύει
  πανομοιότυπα είτε από κάτω τρέχει Apple Clang, MinGW-w64 GCC, ή GCC σε
  Ubuntu.
- Τα warnings (`-Wall -Wextra`, ήδη ενεργά στο CMakeLists.txt) πιάνουν τα
  ίδια βασικά λάθη αρχαρίων (αχρησιμοποίητες μεταβλητές, λάθος format
  specifiers, κ.λπ.) και στους δύο compilers — η ακριβής διατύπωση του
  μηνύματος διαφέρει ελαφρώς, κάτι αμελητέο σε αυτό το επίπεδο μαθήματος.

**Πρακτικό συμπέρασμα:** εγκαταστήστε μόνο τα Xcode Command Line Tools
(`xcode-select --install`) και το CMake (`brew install cmake`). Μην
προσθέσετε GCC στο Mac σας — απλά επιπλέον βάρος χωρίς πραγματικό όφελος
εδώ.

### Αρχή σχεδιασμού: IDE ξεχωριστό από compiler/build system

Όπως ζητήσατε, το IDE (VS Code, CLion, ή στα Windows το Dev-C++) **δεν
είναι ποτέ** αυτό που αποφασίζει πώς μεταγλωττίζεται ο κώδικας — αυτό το
κάνει αποκλειστικά το ζευγάρι **CMake + compiler**. Το IDE είναι απλώς ένα
«παράθυρο» πάνω στο ίδιο CMake project. Πρακτικά αυτό σημαίνει:

- Μπορείτε να αλλάξετε IDE (π.χ. από VS Code σε CLion, ή έναν μαθητή από
  Dev-C++ σε Code::Blocks) **χωρίς καμία αλλαγή** στο `CMakeLists.txt` ή
  στον πηγαίο κώδικα.
- Κάθε IDE απλώς καλεί τις ίδιες δύο εντολές (`cmake -S . -B build`,
  `cmake --build build`) πίσω από τα σκηνικά, ή σας αφήνει να τις τρέξετε
  εσείς απευθείας στο τερματικό — το αποτέλεσμα είναι πάντα ίδιο.
- Αν αύριο αλλάξετε compiler (π.χ. δοκιμάσετε LLVM Clang αντί για Apple
  Clang), και πάλι δεν αλλάζει τίποτα στο IDE setup.

### Σημείωση για Intel Mac συγκεκριμένα

Οι οδηγίες `xcode-select --install` και `brew install cmake` είναι
ταυτόσημες σε Intel και Apple Silicon Mac — δεν υπάρχει διαφοροποίηση.
Το μόνο τεχνικό σημείο που αλλάζει μεταξύ αρχιτεκτονικών είναι το directory
όπου εγκαθιστά το Homebrew τα πακέτα (σε Intel: `/usr/local`, σε Apple
Silicon: `/opt/homebrew`) — κάτι που ο ίδιος ο installer του Homebrew το
ρυθμίζει αυτόματα στο PATH σας, οπότε δεν χρειάζεται καμία χειροκίνητη
ενέργεια εκ μέρους σας. Δεν υπάρχει καμία εξάρτηση από Rosetta 2 σε αυτό
το setup — όλα (Apple Clang, CMake, VS Code, CLion) τρέχουν φυσικά (native)
σε Intel.

### Η μία πραγματική παγίδα φορητότητας να προσέξετε: το `long`

Ανεξάρτητα από Clang/GCC, υπάρχει μια *πραγματική* διαφορά μεταξύ
Windows και macOS/Linux: στα Windows (και με MinGW ΚΑΙ με MSVC), ο τύπος
`long` είναι **4 bytes**, ενώ σε macOS/Linux είναι **8 bytes** (διαφορά
μοντέλου ABI, LLP64 vs LP64 — άσχετο με τον compiler). Αν κάποιο πρόγραμμα
βασίζεται σε `long` για «μεγάλους» αριθμούς, το εύρος του θα διαφέρει
ανάλογα με το OS. Λύση: για φορητότητα, προτιμήστε `long long` (πάντα 8
bytes) ή τους τύπους σταθερού πλάτους από το `<stdint.h>` (`int64_t`).
Το υλικό του μαθήματος το αποφεύγει ήδη, αλλά καλό είναι να το έχετε υπόψη
σας σε μελλοντικές ασκήσεις.

## 2. Πρόταση Setup ανά Περιβάλλον

### MacBook (Intel, macOS Sequoia) — το δικό σας μηχάνημα ανάπτυξης

```bash
xcode-select --install     # Apple Clang + βασικά εργαλεία
brew install cmake         # CMake
brew install git           # αν δεν υπάρχει ήδη
```

IDE: **VS Code** ή/και **CLion**, και τα δύο ανοίγουν απευθείας τον φάκελο
του αποθετηρίου (εκεί που βρίσκεται το `CMakeLists.txt`) — και τα δύο
ανιχνεύουν αυτόματα το CMake project και τον Apple Clang.

- **VS Code**: εγκαταστήστε τις επεκτάσεις **"C/C++" (Microsoft)** και
  **"CMake Tools"**. Το CMake Tools σάς αφήνει να επιλέξετε "kit" (θα δει
  αυτόματα το Apple Clang) και προσφέρει build/debug με ένα κλικ.
- **CLion**: ανοίξτε τον φάκελο του project — το CLion καταλαβαίνει το
  `CMakeLists.txt` αμέσως, χωρίς επιπλέον ρύθμιση. Ιδανικό για βήμα-βήμα
  debugging με οπτικό interface (πολύ χρήσιμο όταν διδάσκετε δείκτες!).

Και τα δύο IDE μπορούν να συνυπάρχουν στο ίδιο repo χωρίς σύγκρουση, **αν
δεν κάνετε commit τα δικά τους ρυθμιστικά αρχεία** — το `.gitignore` του
project ήδη αγνοεί τα `.vscode/` και `.idea/`.

### Windows (μηχανήματα εργαστηρίου) — δεν κάνουν push στο remote

Το Dev-C++ που υπάρχει ήδη στα εργαστήρια συχνά έρχεται με πολύ παλιό
bundled compiler (TDM-GCC/MinGW, μερικές φορές από την εποχή του C99 ή και
παλιότερο) που **δεν** υποστηρίζει πλήρως C11. Προτάσεις, σε σειρά
προτίμησης:

1. **Καλύτερη λύση:** εγκαταστήστε **MSYS2** (msys2.org) και μέσα από αυτό
   ένα σύγχρονο **MinGW-w64 GCC**:
   ```
   pacman -S mingw-w64-ucrt-x86_64-gcc mingw-w64-ucrt-x86_64-cmake
   ```
   Οι μαθητές συνεχίζουν να γράφουν κώδικα στο Dev-C++ (ή σε ό,τι
   editor προτιμούν) αλλά η **μεταγλώττιση/εκτέλεση** γίνεται μέσω CMake
   από το τερματικό MSYS2 — ίδιες εντολές με το BUILD.md.
2. **Εναλλακτικά**, αν θέλετε να μείνετε 100% μέσα στο Dev-C++: ελέγξτε αν
   η έκδοσή σας επιτρέπει να ενημερώσετε το bundled TDM-GCC σε πιο
   πρόσφατη έκδοση (Dev-C++ 6.3+ έρχεται με TDM-GCC 9, που υποστηρίζει
   C11 αρκετά καλά).
3. Σε κάθε περίπτωση, εγκαταστήστε **CMake for Windows** (cmake.org) ώστε
   να δουλεύουν οι ίδιες εντολές `cmake -S . -B build` / `cmake --build
   build` που περιγράφονται στο [`docs/BUILD.md`](BUILD.md).

Καθώς αυτά τα μηχανήματα δεν κάνουν push προς το αποθετήριο, δεν χρειάζεται
να ανησυχείτε για git conflicts — απλά τραβούν (`git pull`) ή αντιγράφουν
το υλικό.

### Ubuntu — περιβάλλον επαλήθευσης/δοκιμών

```bash
sudo apt update
sudo apt install build-essential cmake git
```

Αυτό είναι το πιο "καθαρό" περιβάλλον GCC, ιδανικό ως σημείο αναφοράς: αν
κάτι μεταγλωττίζεται εκεί χωρίς προειδοποιήσεις, σχεδόν σίγουρα θα
δουλέψει παντού. Μπορείτε να χρησιμοποιήσετε είτε VS Code είτε CLion εκεί
επίσης, για οπτική συνέπεια με το Mac σας.

> Σημείωση: όλο το παρόν αποθετήριο (180 προγράμματα) έχει ήδη χτιστεί και
> ελεγχθεί επιτυχώς σε περιβάλλον Ubuntu 24.04 με GCC 13, ως μέρος της
> προετοιμασίας αυτού του υλικού — μηδέν σφάλματα μεταγλώττισης, μηδέν
> crashes σε δοκιμαστική εκτέλεση με δείγματα εισόδου.

## 3. Ροή Git (Git Workflow)

Όπως περιγράψατε, η σχέση κάθε περιβάλλοντος με το remote (π.χ. GitHub)
δεν είναι συμμετρική. Η προτεινόμενη τοπολογία:

```
                    ┌─────────────────────┐
                    │   Remote (GitHub)   │
                    └──────────┬──────────┘
                     push ▲     │ pull/clone
                           │     ▼
        ┌──────────────────────┐   ┌─────────────────────────┐
        │   MacBook (Intel)    │   │  Windows εργαστηρίου (Ν  │
        │  push ΚΑΙ pull       │   │  μηχανήματα) — ΜΟΝΟ pull │
        │  = «αρχή αλήθειας»   │   │  ή clone, ΠΟΤΕ push      │
        └──────────────────────┘   └─────────────────────────┘
```

- **MacBook = το μόνο σημείο που κάνει push.** Όλες οι αλλαγές στο υλικό
  του μαθήματος (νέες ασκήσεις, διορθώσεις σημειώσεων, κ.λπ.) γίνονται
  εκεί, με κανονικό `git add / commit / push`.
- **Windows εργαστηρίου = μόνο κατανάλωση, ποτέ πηγή αλλαγών.** Στην αρχή
  κάθε εργαστηριακού μαθήματος, οι μαθητές κάνουν `git pull` (αν έχουν ήδη
  clone το repo από πριν) ή `git clone` (πρώτη φορά) για να πάρουν το πιο
  πρόσφατο υλικό. Δεν χρειάζεται καν λογαριασμός με δικαιώματα εγγραφής
  στο remote για τα μηχανήματα του εργαστηρίου — αρκεί read-only πρόσβαση
  (π.χ. clone μέσω HTTPS χωρίς credentials, αφού το repo θα είναι public ή
  με απλό read-only deploy key).
- **Ubuntu:** δεν το προσδιορίσατε ρητά στη ροή git, οπότε το αντιμετωπίζω
  ως ένα τρίτο, ανεξάρτητο **περιβάλλον επαλήθευσης** (π.χ. VM ή container
  όπου απλά κάνετε `git pull`/`clone` για να επιβεβαιώνετε ότι το υλικό
  χτίζεται καθαρά σε «σκέτο» Linux/GCC πριν το παρουσιάσετε) — όχι σημείο
  push. Αν στην πραγματικότητα θέλετε να γράφετε/επεξεργάζεστε υλικό κι
  εκεί, πείτε το και προσαρμόζω την τοπολογία.

Πρακτική συνέπεια για τα Windows μηχανήματα: επειδή ποτέ δεν κάνουν push,
δεν υπάρχει κίνδυνος να «λερώσουν» το ιστορικό του repo με τοπικές αλλαγές
μαθητών (π.χ. αρχεία `.txt` που παράγουν τα προγράμματα της Εβδομάδας 15,
ή προσωπικά πειράματα σε ασκήσεις) — αυτά μένουν αποκλειστικά τοπικά στο
κάθε εργαστηριακό μηχάνημα και αγνοούνται ούτως ή άλλως από το `.gitignore`.

## 4. Συνοπτικός Πίνακας

| Περιβάλλον | Compiler | Build | IDE πρόταση |
|---|---|---|---|
| macOS (Intel, Sequoia) | Apple Clang (Xcode CLT) | CMake (Homebrew) | VS Code ή/και CLion |
| Windows (εργαστήριο) | MinGW-w64 GCC (μέσω MSYS2) | CMake (installer) | Dev-C++ (editor) ή VS Code |
| Ubuntu | GCC (`build-essential`) | CMake (`apt`) | VS Code ή CLion |

Σε όλες τις περιπτώσεις, ο μαθητής/εκπαιδευτής τρέχει τις **ίδιες δύο
εντολές**:

```bash
cmake -S . -B build
cmake --build build
```

— βλ. [`docs/BUILD.md`](BUILD.md) για πλήρεις οδηγίες, ανά OS.
